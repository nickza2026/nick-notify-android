# Sign in with Google สำหรับเจ้าของหนึ่งบัญชี — คู่มือ operator

เอกสารนี้เป็นขั้นตอนเตรียมและตรวจสอบการเปลี่ยนวิธี login ของ **เจ้าของเดิม** ทั้ง Dashboard และ Android; ไม่ใช่หลักฐาน rollout จริง และไม่อนุญาตให้ deploy, dispatch CI, ส่ง FCM จริง หรือแก้ฐาน production โดยอัตโนมัติ สัญญาฝั่ง browser อยู่ที่ [FE contract](fe-google-login-th.md); แบบจำลองฐานแก้ไขได้ใน [DBML สำหรับทบทวน](google-owner-login.dbml) ซึ่ง **ยังไม่อนุมัติ**.

## ก่อนเปลี่ยนระบบ

1. ตรวจว่า API/Web/Android ที่จะใช้รองรับ Google login, มี PostgreSQL schema ปัจจุบันรวม migration `004_google_owner.sql` และมี `dashboard_owner` **เดิม** เพียงบัญชีเดียว (`id=1`); การผูก Google ไม่สร้าง owner ให้ผู้เข้าระบบคนแรก ฐานใหม่ต้อง bootstrap owner ด้วย `DASHBOARD_ADMIN_USERNAME` และ `DASHBOARD_BOOTSTRAP_PASSWORD` ตาม [คู่มือ runtime เดิม](dashboard-runtime-th.md) ผ่าน private runtime configuration ก่อน; restart ไม่เปลี่ยน owner เดิม. สำรองฐาน ตรวจสิทธิ์ migration และแผนย้อนกลับก่อนอนุมัติการใช้ฐานจริงแยก.
2. ระบุ Firebase project **เดียวกัน** สำหรับ Web SDK, Android client และ `FIREBASE_PROJECT_ID`; อย่าสลับ Firebase project กับ FCM โดยเดา. Firebase Authentication ใน Firebase Console → Sign-in method → เปิด provider **Google** และตั้งค่าที่ Console ขอให้ครบ. เพิ่ม Web app ใน Project settings และตรวจ `apiKey`, `authDomain`, `projectId`, `appId` ของ Web app จริง. ใน Authentication → Settings → Authorized domains ตรวจและเพิ่ม public Dashboard domain จริง; หากทดลอง loopback ให้เพิ่ม `localhost` เองตามที่ Console อนุญาต (โครงการ Firebase ใหม่หลัง 28 เม.ย. 2025 ไม่เพิ่ม `localhost` ให้อัตโนมัติ). ต้องใช้ canonical origin ของ Web จริง; HTTP อนุญาตเฉพาะ loopback ในแอปนี้. การอนุญาตโดเมนไม่ใช่การอนุญาต UID เป็น owner.
3. เตรียม Web server configuration ผ่านช่องทาง deployment ส่วนตัว: `FIREBASE_WEB_API_KEY`, `FIREBASE_WEB_AUTH_DOMAIN`, `FIREBASE_WEB_PROJECT_ID`, `FIREBASE_WEB_APP_ID` จาก Web app; public Firebase SDK configuration สี่ค่านี้ถูกส่งให้ browser โดยตั้งใจ แต่ไม่ใช่ backend app key และต้องจำกัดการใช้ API key ตามนโยบาย Firebase. ใช้ `DASHBOARD_PUBLIC_URL`, `BACKEND_URL`, `BACKEND_API_KEY` หรือ `BACKEND_API_KEY_FILE` ตาม [คู่มือ runtime](dashboard-runtime-th.md). ห้ามใส่ `ALERT_API_KEY`, service-account JSON หรือ DB credentials ใน browser/APK. `GOOGLE_APPLICATION_CREDENTIALS` ในคู่มือ runtime สำหรับ FCM sender ไม่ใช่ Web SDK config, ไม่ใช่ Android `google-services.json`, และตัวตรวจ Firebase ID token ฝั่ง API นี้ไม่ต้องมี service-account key เพื่อทำ public-certificate verification.

## หา Firebase UID ให้ถูกก่อนผูก owner

เมื่อ Web มีสี่ค่า Firebase ข้างต้นแล้ว เปิด `/google-account` บน Web origin ที่เชื่อถือได้ ใช้ปุ่มเลือก **บัญชี Google ของเจ้าของจริง**; หน้าเรียก `GET /api/auth/google-setup` เพื่อรับเฉพาะ public Web Firebase configuration แม้ยังไม่มี backend, master key, local session หรือ `FIREBASE_OWNER_UID`. Firebase SDK sign-in อาจสร้าง Firebase Authentication user ครั้งแรกใน project นั้น แต่ **ไม่สร้าง Notify owner**, ไม่ให้สิทธิ์ Dashboard/device, ไม่ส่ง UID ไป Go API, ไม่แลก token กับ backend และไม่แสดง ID token. คัดลอก **Firebase UID** ที่หน้าจอแสดงผ่านช่องทาง private configuration ไปตั้ง `FIREBASE_OWNER_UID` ฝั่ง API; UID นี้ **ไม่ใช่** Google OAuth `sub`, อีเมล, OAuth client ID, project ID หรือ legacy username. ตรวจ project/account ที่เลือกและสิทธิ์เข้าถึงก่อนอนุมัติ bind; ห้ามโพสต์ UID/credential เพื่อให้คนอื่นตั้งค่าแทน. หลังการตรวจ Web Firebase Auth ใช้ in-memory persistence และพยายาม sign out ใน `finally`; ไม่ใช่การเพิกถอน local session ที่ออกไปแล้ว.

## ตั้งค่า API และ cutover

ตั้ง `AUTH_MODE=google`, `FIREBASE_PROJECT_ID=<PROJECT_ID_OF_SAME_FIREBASE_PROJECT>` และ `FIREBASE_OWNER_UID=<EXACT_FIREBASE_UID_OF_OWNER>` ใน **API private runtime config**; ใช้ค่า owner UID ที่ตรวจเองเท่านั้น ไม่เปิด anonymous/public signup หรือโหมดที่ผู้ login คนแรกเลือก owner ได้. หากยังไม่พร้อม ให้คง password mode เดิมก่อน cutover; หลังผูกแล้ว **ห้าม** ถือว่าการสลับ `AUTH_MODE=password` หรือ unset เป็น rollback: การผูกถาวรป้องกัน password downgrade และ password login/change ตอบ `403 password_auth_disabled`. การเปลี่ยน UID/project หลังผูกไม่โอน owner อัตโนมัติ แต่ทำให้ auth ไม่พร้อม (`503 google_auth_unavailable`); อย่าลบ/แก้ binding เพื่อแก้ login โดยไม่อนุมัติและออกแบบวิธีย้าย owner แยก.

ตัวตรวจ Google ไม่รองรับ Firebase Auth Emulator: `FIREBASE_AUTH_EMULATOR_HOST` ต้องว่าง. การสร้าง verifier ปฏิเสธ `GOOGLE_API_USE_CLIENT_CERTIFICATE=true` และ `EXPERIMENTAL_GOOGLE_API_USE_S2A=true` เพื่อไม่ค้น private client certificate หรือ metadata ของเครื่อง. ใช้ Firebase project ที่ระบุชัดเจนและ public certificate verification โดยไม่ค้น Application Default Credentials; ไม่จำเป็นต้องเพิ่ม service-account key สำหรับการตรวจ login นี้.

การ activate ครั้งแรกต้องพบ owner เดิม แล้วผูก Firebase project+UID แบบ singleton และเพิกถอน **web/native local sessions ทั้งหมดครั้งเดียว**. Restart ด้วย config ที่ตรง binding จะไม่ revoke ซ้ำ; login ใหม่ใช้ Firebase ID token ของ UID เดิม, provider `google.com`, verified email และไม่เป็น tenant token. Go ตรวจ Firebase ID token ตอน **exchange** ด้วย SDK `VerifyIDToken` ไม่ใช้ Google OAuth token ตรง ๆ; ไม่ตรวจ token revoked/disabled ด้วย remote lookup ทุกคำขอ. การ sign out จาก Google/Firebase, เปลี่ยน provider configuration หรือ disable Firebase user ไม่ได้เพิกถอน local sessions ที่ออกแล้วโดยอัตโนมัติ (Web สูงสุด 24 ชม.; Android สูงสุด 30 วันและต่ออายุได้เมื่อ register สำเร็จ). ต้องเพิกถอน local sessions แยกหากต้องการตัดสิทธิ์ทันที; คำขอที่ผ่านตรวจสิทธิ์ก่อน revoke อาจจบต่อได้.

หาก Google config ขาด/ผิดหรือ Firebase public certificate fetch/verification ล้มเหลว Google auth จะไม่พร้อมหรือ login ถูกปฏิเสธ; **อย่า fallback ไป password**. กรณีฉุกเฉิน `AUTH_MODE=google` โดยไม่มี owner UID ที่ใช้ได้จะปิด protected Dashboard/client auth ด้วย `503` แต่ไม่ใช่ kill switch สำหรับ alert service ที่ใช้ application key หรือ Ack capability; pending/offline Ack และ critical alarm ที่เริ่มแล้วไม่หยุดด้วยการเปลี่ยน auth/revoke. การผูก/revoke รักษาอุปกรณ์, encrypted FCM tokens, routing, ประวัติ และ Ack capabilities; ไม่รับประกันว่า FCM ส่งถึงหรือเสียงดังจริง.

## เตรียม Android client และ APK อย่างระมัดระวัง

ใน Firebase Project settings → Android app ให้เลือก package `dev.notifyalarm` และลงทะเบียน **SHA-1 และ SHA-256 ของ signing certificate ตัวเดิม** ที่ใช้กับ APK บนโทรศัพท์; ตรวจจาก certificate ต้นทางที่เจ้าของเชื่อถือได้ ไม่ใช้ลายเซ็น debug ใหม่แทน. Workflow guard pin SHA-256 สาธารณะ `79c26a1c9329aa69933eada6c5e13b7718d43ae1da90120de639fe23f10cc9d4` แต่ค่านี้ไม่ใช่ SHA-1. หลังเปิด Google provider และเพิ่ม fingerprints ให้ดาวน์โหลด Android `google-services.json` **ฉบับอัปเดต** จาก Firebase Console เก็บไว้ใน private path นอก Git. จาก root repository จึงใช้:

```powershell
.\scripts\configure-firebase.ps1 -GoogleServicesJson 'C:\private\google-services.json'
```

Script เลือก Android client `dev.notifyalarm` หนึ่งรายการ สร้าง `app/src/main/res/values/firebase-local.xml` ที่ gitignore จาก project/app/sender/API key; ถ้าพบ `oauth_client` ประเภท Web (`client_type=3`) **หนึ่งรายการ** จะสร้าง `default_web_client_id` ด้วย หากพบหลายรายการหรือ project number ไม่ตรงจะล้มเหลว; JSON รุ่นเก่าที่ไม่มี Web OAuth client ยังสร้าง resource สี่ค่าได้ แต่ Google login ใช้ไม่ได้จนได้ JSON ฉบับอัปเดตที่มี Web client ID. Resource/Web client ID นี้เป็น client config ไม่ใช่ service-account key หรือ backend application key. Android ใช้ Credential Manager ขอ Google ID token แล้ว `FirebaseAuth.signInWithCredential` เพื่อขอ **Firebase ID token** ไปแลกที่ API; หลังแลกมีการเรียก `FirebaseAuth.signOut()` แบบ asynchronous flow อย่าอ้างว่า Firebase Auth บน Android เป็น zero-persistence โดยเฉพาะเมื่อ process ตายระหว่างทาง.

Metadata ของรุ่นแก้ไขใน source/workflow เป็น `versionCode=10`, `versionName=0.9.1-google-setup`; workflow manual บน `main` ยังคง signer SHA-256 guard เดิม และการ publish update ต้อง opt-in แยก. รุ่นก่อนหน้า `0.9.0` ผ่าน signed CI run `44273335213` และเผยแพร่เป็น `android-v0.9.0-google-owner` โดยผู้ใช้อนุมัติแล้ว ส่วนรุ่น `0.9.1` ยังไม่ได้ build ผ่าน signed CI หรือเผยแพร่. APK local/debug ไม่ใช่หลักฐานว่าเซ็นด้วย original certificate; ไม่ถอนแอป/reset ข้อมูลเพื่อข้าม signer mismatch.

รุ่น `0.9.1` เตรียม API URL ของบริการนี้และชื่อเครื่องจากรุ่นอุปกรณ์ให้เอง รักษา URL/ชื่อเดิมเมื่อมี session อยู่ และตรวจ auth mode อัตโนมัติเมื่อเปิดหน้า ช่องตั้งค่าเองอยู่ใน “ตั้งค่าขั้นสูง”. ปุ่ม Sign in with Google ไม่ถูกซ่อนเมื่อรอ config หรือเกิด network error แต่จะเปิดให้กดเมื่อบริการตอบ mode `google` เท่านั้น; mode `password` แสดงว่ายังต้องเปิด Google ที่ runtime ไม่ใช่ให้ตั้งบัญชีใหม่บนมือถือ. การเปลี่ยน URL/ปิดหน้า/คำตอบเก่าต้องไม่เปลี่ยนสถานะของการเข้าสู่ระบบใหม่ และไม่หยุดเสียงปลุกหรือรับทราบเหตุการณ์แทนผู้ใช้.

## ตรวจความพร้อมและเพิกถอนกรณีจำเป็น

- ก่อน cutover ตรวจ Web `/google-account` ว่าแสดง UID จาก project/account ที่ตั้งใจโดยไม่สร้าง Notify session; อย่าใช้ UID/อีเมลที่ผู้ใช้ส่งมาเป็นหลักฐานแทนการตรวจของ operator. เมื่อ API พร้อม `GET /api/auth/config` ควรได้ `mode=google`, `firebase_project_id` ตรง Web `firebase.projectId`; Android `GET /v1/client/auth-config` ต้องได้ project ตรง APK; mismatch หยุด ไม่กลับไป password. การตรวจ endpoint ไม่แทนการพิสูจน์ browser popup/Google จริง, Android เครื่องจริง, FCM/Ack หรือ upgrade signature.
- ถ้าจำเป็นต้องตัด local session ทั้งหมด **หลังได้รับสิทธิ์ต่อฐานเป้าหมาย** ใช้ standalone `notify-admin` ที่ build จาก `backend/cmd/notify-admin` ตามข้อจำกัดไฟล์ URL/ACL/TLS/PG environment ใน [คู่มือกู้บัญชี](dashboard-owner-recovery-th.md). `owner show` อ่านชื่อ owner ที่มีอยู่ก่อน แล้วใช้ชื่อ case-sensitive ที่แสดงเป็น `EXACT_OWNER_FROM_SHOW`:

```powershell
Set-Location backend
go build -o notify-admin.exe ./cmd/notify-admin
.\notify-admin.exe owner show --db-url-file 'C:\private\db-url.txt'
.\notify-admin.exe owner revoke-sessions --db-url-file 'C:\private\db-url.txt' --confirm-username 'EXACT_OWNER_FROM_SHOW'
```

ตัวอย่าง path เป็น placeholder ส่วนตัว ไม่ใช่ไฟล์จริงหรือคำสั่งที่ได้รันแล้ว. คำสั่ง revoke ลบเฉพาะ web/native local sessions ทั้งหมด; ไม่ลบ owner hash/binding, อุปกรณ์, ประวัติหรือ Ack และไม่ห้าม Google login ครั้งถัดไป. `reset-password` ของบัญชีที่ผูก Google **ไม่เปิด password login อีก**; ให้ใช้ `revoke-sessions` สำหรับการตัด session แทน. หากสงสัย account compromise ให้จัดการ Firebase account/provider และการอนุมัติ rollout แยก; การ revoke ไม่หยุด critical alarm ที่เริ่มทำงานหรือยกเลิก pending Ack.

ขอบเขตที่ยืนยัน: local Go tests/vet/build, Android unit/build/lint, Web tests/typecheck/isolated production build และ browser กับ backend สังเคราะห์. วันที่ 18 พ.ย. 2026 Google จริงจาก Web ผ่าน Go verifier/local session และผู้ใช้ยืนยันเข้าถึง Dashboard โดยใช้ PostgreSQL แยกและไม่เปิด FCM sender. API/Web workflow ของ merge `2b5e0b96` ผ่าน deploy jobs; public API auth-config ตอบ `password`. APK `0.9.0` ผ่าน signed CI, ตรวจ public feed/descriptor/download hash และผู้ใช้รายงานอัปเดตสำเร็จแล้ว แต่ Google login บนมือถือ/บริการจริงและ FCM/Ack รอบใหม่ยัง **ไม่ได้ยืนยัน**. การแก้ onboarding `0.9.1` ต้องแยกหลักฐานจาก release `0.9.0` เดิม.
