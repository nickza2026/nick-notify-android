# Notify Alarm API (PostgreSQL)

Go 1.25+, PostgreSQL 16-compatible SQL. This backend now uses PostgreSQL exclusively; the former Firestore source is archived as whitelisted code only in `../artifacts/firestore-source-baseline.zip`. Neither database's records are migrated or deleted. The existing PostgreSQL schema is embedded in `migrations/001_init.sql` and applied idempotently on startup before listening; inspect/backup an existing production database and authorize any data migration separately. Do not publish secrets or tokens.

The database must use UTF8. Startup checks `server_encoding` before migration and rejects other encodings without converting existing data. Embedded tests/demo explicitly initialize UTF8, independent of Windows locale (which otherwise can select WIN874). Canonical idempotency replay precedes new-payload size checks; timestamp formatting changes cannot turn an existing accepted receipt into a spurious 422.

## Run and safety

Production: provide `DATABASE_URL` (explicit PostgreSQL connection string), `ALERT_API_KEY` (random, at least 32 bytes), and run `go run ./cmd/notify-api`. No implicit database/embedded PostgreSQL startup or inherited credential fallback is permitted. `HOST` defaults to `127.0.0.1`; `PORT` to `8791`. Configure external TLS termination, network ACLs, backups, retention and monitoring. FCM sending also requires both `GOOGLE_APPLICATION_CREDENTIALS` (selected service-account file) and `FCM_DEVICE_TOKEN`; otherwise alert POST returns 503, while authenticated history remains available. `ACK_PUBLIC_BASE_URL` enables capability ACK URLs and must be canonical HTTPS without query/fragment/credentials/percent escapes. Do not set an unreachable public URL. Credentials and DB connection strings must not be logged.

Isolated tests: `go test ./... -count=1 -timeout=8m` starts its **own** embedded PostgreSQL per integration test on loopback, applies the same migration and runs with a fake sender. Tests do not connect to inherited `DATABASE_URL`, Docker, cloud Firestore or real FCM. Missing embedded PostgreSQL is a test failure, not a skip. Embedded PostgreSQL 16.9 public binaries use a shared cache at `NOTIFY_PG_CACHE` or the OS user cache under `notify-alarm/embedded-postgres`; only runtime/data directories owned by a test are removed. The cache persists. `go test ./... -run '^TestPure' -count=1` tests only pure protocol/FCM code, not database behavior.

Synthetic loopback demo: `go run ./cmd/dev --synthetic --port=8791 --stop-file=<nonexistent-path>` starts its own ephemeral embedded database, seeds six Thai synthetic incidents (exactly one normal unacknowledged accepted `demo_storage`, the others critical; three ACK links from two shared action UUIDs), uses a fake sender, and binds only `127.0.0.1`. Ctrl+C, SIGTERM, or creating the stop file gracefully shuts down and removes only this process's temporary database directories; the shared archive cache is not removed. `ALERT_API_KEY` can override the local-only key `synthetic_demo_api_key_not_for_production_0001`. This never sends real FCM. Synthetic `provider_accepted` means only the fake sender returned successfully, not that any handset was contacted. Use an explicit date range for UI tests near Bangkok midnight: fixture timestamps are relative to demo start.

## Schema and consistency

`alerts` stores hashed idempotency keys, normalized body digests and hashed 32-byte random ACK capabilities; it never stores the plaintext tokens or API key. `ack_actions` stores normalized individual rows keyed by `(alert_id,client_action_id)`; no artificial Firestore 4,000-action document limit applies. POST commits a unique-key alert reservation **before** invoking the sender, and provider side effects never run in retryable transactions. A crash or ambiguous in-flight reservation remains `delivery_unknown`; replay returns 409 `delivery_unknown_or_in_progress` and never resends. Completed outcomes are durable. ACK locks the alert row, inserts only a new UUID, and keeps `first_ack_at` immutable. Last ACK is maximum server receipt, including when the clock moves backward. Detail GET uses one repeatable-read snapshot; keyset history is ordered by `(created_at DESC,id DESC)` and ties remain stable. No destructive schema commands or automatic data transfer are executed. The idempotent migration backfills missing first ACK from the earliest historical action; back up before production upgrades.

## HTTP protocol

Importance contract: POST `/v1/alerts` accepts optional `"importance":"normal"|"critical"`; omission defaults to `critical`, while null/unknown values fail with 4xx. Both create receipts and GET detail/history include the normalized string. Critical preserves continuous alarm until human Ack and HIGH FCM transport; normal is notification-only (no sound, vibration or fullscreen) and uses NORMAL FCM transport, which can be deferred. FCM data always includes `importance` within the 4,000-byte budget; `type=alert` remains for critical and legacy requests, while normal uses `type=notice`. Older APKs ignore unknown `notice` messages rather than risk escalating a normal notification to an alarm; upgrade the Android client to receive normal notices. Omitted and explicit critical retain the original idempotency digest; changing mode with the same key conflicts. PostgreSQL migration adds checked NOT NULL `importance` with default critical to existing rows without replacing their contents.

Server-generated times are canonical UTC microseconds before persistence/first response, so replay and ACK retry timestamps agree. All responses disable caching. `delivery_verified` is always false. `Authorization: Bearer <ALERT_API_KEY>` is required for POST `/v1/alerts`, GET `/v1/alerts/{id}`, GET `/v1/history`, GET `/v1/stats`. Per-process quotas and default four concurrent operations are coarse limits, not distributed DDoS protection. Public GET `/health` reports configuration only.

POST `/v1/alerts` requires `Idempotency-Key` (1–128 ASCII alphanumeric or `_.:-`) and JSON up to 16,384 bytes, e.g. `{"alert_id":"incident_42","title":"Smoke detected","message":"Check floor 2","ttl_seconds":300}`. ID is optional (1–100 alphanumeric/dash/underscore); title ≤120 characters, message ≤2000; TTL defaults 300 and ranges 30–10800 seconds. Unknown fields/nulls are invalid. The FCM data budget is 4,000 serialized UTF-8 bytes including capability URL and importance; critical uses Android priority HIGH, normal uses NORMAL, and provider TTL cannot exceed remaining playback-start window. Successful example HTTP 202: `{"alert_id":"incident_42","status":"provider_accepted","expires_at":"2026-10-20T02:00:00Z","acknowledged":false,"delivery_verified":false}` (timestamp illustrative). This is provider acceptance, **not** device delivery. Definite rejection HTTP 502: `{"alert_id":"incident_42","status":"provider_failed","error":{"code":"provider_rejected"},"delivery_verified":false}`; ambiguous outcome HTTP 502: `{"alert_id":"incident_42","status":"delivery_unknown","error":{"code":"provider_delivery_unknown"},"delivery_verified":false}`. Concurrent/pending/crashed same-key replay returns HTTP 409 with `error.code=delivery_unknown_or_in_progress`; completed same-key replay returns original 202/502 with `Idempotency-Replayed: true`, **never resends**. A changed body or duplicate explicit ID returns 409 (`idempotency_conflict`/`alert_id_conflict`). Storage outage returns 503; no send occurs without committed reservation.

POST `/v1/alerts/{id}/ack` takes the separate per-alert 43-character capability bearer and JSON `{ "client_action_id":"UUID optional", "client_acked_at":"RFC3339 optional" }`. Transient capability lookup failure returns **503**, not a permanent 401; invalid/missing capabilities return 401. Android must reuse **one UUID per human Ack-all tap** across selected alerts and retries; `(alert_id,client_action_id)` counts once, omitted ID maps to stable legacy action for that alert. `received_at` is authoritative, optional client time telemetry only. An ACK remains valid after playback expiry. Response fields: `alert_id,status:"acknowledged",acknowledged_at,ack_count,last_ack_at`. An ACK never changes the original provider status.

GET `/v1/alerts/{id}` returns provider status, first/last ACK times/count, `acknowledged` boolean, ordered `ack_actions:[{client_action_id,client_acked_at,received_at}]` (empty array, not null) and `delivery_verified:false`, with no capabilities. GET `/v1/history?from=RFC3339&to=RFC3339&status=all|provider_accepted|provider_failed|delivery_unknown|acknowledged|pending_ack&limit=25&cursor=opaque` returns `items` and `next_cursor`; limit 1–100. Inclusive `from`, exclusive `to`, based on alert creation. Cursor binds both date bounds and status; provider outcome remains immutable. `pending_ack` is provider accepted with no ACK, including expired playback windows. GET `/v1/stats?from=&to=` returns `total_alerts,provider_accepted,provider_failed,delivery_unknown,acknowledged,pending_ack,ack_action_count`; the last globally deduplicates action UUID across selected alerts. Date scopes are creation times. All timestamps are UTC with `Z`.
